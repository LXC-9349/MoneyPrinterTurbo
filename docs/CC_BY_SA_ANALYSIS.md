# CC BY-SA 素材：利弊分析与自动署名方案（决策文档）

> 状态：**仅分析与设计，未改动任何白名单/代码**。是否放行 CC BY-SA 由维护者决定。
> 关联代码：`app/services/archives/wikimedia.py`（`_ALLOWED_LICENSE_PATTERNS` /
> `_REJECTED_LICENSE_PATTERNS`，当前用 `sa\b`、`share[- ]?alike` 明确拒绝）、
> `app/services/archives/__init__.py`（注释：CC BY-SA 因 ShareAlike 会强制整片再授权而被排除）、
> `app/services/compliance.py`（授权汇总 `_license_summary`、导出闸门、`build_watermark_clip`）、
> 素材登记表 `assets`（字段：`provider/license/license_url/author/source_page/source_title`）。

## 1. 背景

当前档案素材（Wikimedia Commons、LoC）只放行**公共领域 / CC0 / CC BY**，明确
排除 **CC BY-SA**。原因是本项目的成片默认投放抖音 / B 站 / YouTube 做商业化传播，
而 CC BY-SA 的 **ShareAlike（相同方式共享）** 条款会把“改编作品的整体授权”传染给
我们，与平台默认的“版权所有、独家分发”预期冲突。

代价是覆盖面：Commons 里大量与人物强相关的历史照片、肖像、地图、文件缩略图是
CC BY-SA（尤其 2.0/3.0/4.0），一刀切拒绝会在“冷门人物”上明显丢失可用素材
（这正是里程碑 4 覆盖率痛点的一部分）。

## 2. CC BY-SA 的两项义务（4.0 为例，逐条对应法律文本）

CC BY-SA = **署名（BY）** + **相同方式共享（SA）** 两条并存义务：

1. **署名（Attribution, BY）**——可履行、可自动化：
   - 标注原作者（提供署名方式 / 移除署名的要求也要遵守）；
   - 标注作品来源与所用许可（含许可链接）；
   - 若做了修改，需说明“已改动”（不要求列出改动明细）。
   - 这是**我们能通过“自动署名”完全满足**的一半。

2. **相同方式共享（ShareAlike, SA）**——难以自动化、是真正的决策点：
   - 任何基于 BY-SA 素材**改编/合成**的演绎作品，**必须整体**以**相同的 CC BY-SA**
     （或官方认定的兼容许可，如 CC BY 4.0 被认为与 BY-SA 单向兼容）发布；
   - 意味着我们**不能再对含 BY-SA 素材的成片主张“全部权利保留”**，且必须向下游
     提供同样可再混编的授权——**无法用一段屏幕文字“抵消”**。

> 关键结论：**自动署名只解决 BY，不解决 SA。** 把 SA 当成“加个字幕就行”是常见误解。

## 3. 利弊分析

### 3.1 放行 CC BY-SA 的收益
- **覆盖率显著提升**，尤其冷门人物：Commons 的历史肖像/文献图很多是 BY-SA；
- 与里程碑 4“素材不足不再静默循环”目标一致，减少缺素材镜头；
- 素材质量/相关性更高（直接是人物图像，而非 b-roll 兜底）。

### 3.2 风险与成本
- **整体再授权风险（SA）**：一旦某镜头用了 BY-SA 素材，法律上倾向把“整片”视为演绎
  作品，需要以 BY-SA 对外提供，削弱独家性与商业控制；
- **平台条款摩擦**：抖音/B 站默认“独家/全版权”预期与 CC BY-SA 的“任何人可再使用”相冲，
  虽不必然违规，但会削弱维权与独家分成；
- **多源混编放大风险**：一支片子混用多来源时，只要有一处 BY-SA，就可能牵动整片授权口径；
- **合规自动化复杂度**：闸门需要区分“仅含 BY（可自动署名即可放行）”与“含 BY-SA（需
  决策整片再授权）”，并把 SA 判定与镜头级使用绑定，复杂度和误判成本上升。

### 3.3 三档可选策略（供决策，不改代码）
| 方案 | 说明 | 适用取向 |
|---|---|---|
| **A 维持现状（不推荐改动）** | 继续硬拒 BY-SA，冷门人物靠 b-roll/AI 图兜底 | 商业独家优先，接受覆盖率损失 |
| **B 分场景放行 + 强制整片 BY-SA** | 仅对“非独家 / 明确愿以 CC 发布”的任务允许 BY-SA，成片整体按 BY-SA 发布并附署名 | 教育/公益向、愿开放再使用的内容 |
| **C 只吸收“署名义务”、剥离“SA”** | 仅放行**许可文本中实际不含 SA** 或**上游已双重许可**（同时给 CC BY / CC0 选项）的素材；真 BY-SA 仍拒 | 折中：扩面但不承担传染风险 |

> 说明：C 的可行性取决于上游是否提供“同一文件的更宽松许可选项”（Commons 偶见
> 作者同时释出 CC BY 版本），不能对纯 BY-SA 文件“当作 CC BY 用”，那将直接违约。

## 4. 自动署名方案（仅设计，覆盖“BY”义务，供 B/C 采用）

### 4.1 数据来源（已具备，无需新增采集）
`assets` / 合规 sidecar 的 `sources` 已逐条保存：
`provider, license, license_url, author, source_page, source_title, asset_id`。
自动署名 = 从这些字段按许可要求拼装文本，**不臆造**（缺 author 则回退来源页）。

### 4.2 署名串生成
- 模板（按语言本地化）：
  `“标题/描述” — 作者，来源：站点（链接），许可：许可名（许可链接）；本作品已作修改。`
- Wikimedia：优先 `Artist` 的纯文本名 + `LicenseShortName` + `license_url` +
  `source_page`；LoC：用 rights 段作者/题录 + 稳定链接；库存（Pexels/Pixabay）：
  平台标准授权名（收尾 #2 已采集），通常不强制画面内署名，仅描述区致谢。

### 4.3 呈现位置（三选一或叠加，按任务参数决定）
1. **片尾致谢卡**：滚动/分页列出全部第三方素材署名（最稳妥、可完整承载链接）；
2. **镜头角标/下三分之一**：在用到第三方素材的镜头短暂显示“图：作者/许可”
   （满足“紧邻署名”，但受竖屏 1080×1920 版面限制，字号与时长需可读性测试）；
3. **发布描述区致谢**：把署名清单写入视频简介/说明（YouTube/B 站可放完整链接）。

> 现有 `compliance.build_watermark_clip`（AI 内容标识水印）与导出闸门已存在，
> 自动署名可复用同一渲染链路与 sidecar 数据，无需另起一套；但署名卡渲染属
> **新增功能**，需要单独的视觉核对（字体、留白、竖屏安全区）。

### 4.4 与 ShareAlike 的配合（B 方案必需）
若走 B（真 BY-SA 素材入片），仅署名**不足以合规**，还需：
- 在导出/发布流程强制产出“**本作品整体以 CC BY-SA 4.0 授权**”声明（片尾或描述区）；
- 在合规闸门把“含 BY-SA 素材”标记为**需整片再授权确认**的阻断项（区别于当前
  `license_missing`），要求操作者显式确认“接受整片 CC BY-SA 发布”，类似现有
  `acknowledge_compliance` 的确认闸；
- 导出 sidecar 记录“本片含 BY-SA 素材 → 整片授权口径 = CC BY-SA”，供追溯。

## 5. 建议
- **默认维持 A**（不改白名单）：商业独家的传播取向与 SA 传染冲突大、风险不对称；
- 冷门人物覆盖率问题优先用里程碑 4 的**逐镜独立检索 + b-roll/AI 兜底 + 缺素材确认屏**
  解决，而不是靠放开 BY-SA；
- 若确有开放发布意愿的专区内容，再以**独立开关 + 强制整片 BY-SA 声明 + 闸门确认**的
  形式小范围启用 B，并补齐 4.3 的署名卡渲染与视觉核对；
- 无论 A/B/C，**自动署名的“BY”部分都值得先落地**（对现有 CC BY 素材也是加分，
  且风险为零），可作为里程碑 4 之后的独立小功能排期。
